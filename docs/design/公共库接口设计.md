# 公共操作库接口设计（草稿 v0.1）

依据：[项目设计v3](项目设计v3.md) 第 2、3 节，以及 [PanUI产品操作规约](../exploration/PanUI产品操作规约.md) 第 3 节。本文只定接口和约束，不含实现代码。每条约束后标注来源。

## 1. 设计原则

1. 脚本只写业务步骤，只能调用本库的原语，不直接操作浏览器或数据库。
2. 字段、按钮、网格从表单 JSON 元数据推导，不手写选择器（规约 §3 表单元数据）。
3. 所有等待都是「等某个具体信号」，不用固定 sleep（规约 §3 定位与等待）。
4. 断言只看数据状态和结果表，不依赖提示文案（规约 §3 流程反馈）。
5. 数据库只读。库里不出现任何环境地址、账号、口令，这些只在本机配置里（项目 AGENTS.md 安全条款）。
6. 金额、利率一律用十进制类型比较，不用浮点。

## 2. 分层与模块

| 模块 | 职责 | 依赖 |
|---|---|---|
| `meta` | 按 FormID 读取并解析表单 JSON：字段、必填、只读、掩码、网格列、动作按钮、数据集到物理表的映射 | 通道 A：服务端磁盘文件；通道 C：`/rest/react/loadjson` 接口拉取 |
| `locator` | 把「字段名」解析为页面上的控件，按组件类型选适配器 | `meta`、`adapters` |
| `adapters` | 每种组件一个适配器，提供 `set`、`get`、`state`（只读、必填、禁用、隐藏） | `locator` 的底层驱动 |
| `waits` | 一组具名等待点（见 §5） | 浏览器驱动 |
| `primitives` | 八个原语 | 以上全部 |
| `evidence` | 截图、查询结果、DB 结果的采集与落盘 | `results/` |
| `dbro` | 只读数据库连接器，Oracle 与信创库两种方言 | 本机配置 |
| `guard` | 核心库完整性校验、版本号、扩展层隔离 | 发布清单 |

## 3. 原语接口（业务语言签名）

所有原语的返回值统一为「步骤结果」：状态（通过、失败、阻塞、无效）、说明、证据路径。

| 原语 | 签名 | 说明与约束 |
|---|---|---|
| 开 | `open(menuPath)`、`open_bill(form, key)`、`pick_from_list(list, 条件)` | 菜单路径来自项目配置；待办列表打开单据的具体实现未确认，先用菜单或查询入口，不用待办双击 |
| 填 | `fill(form, {字段: 值})`、`fill_grid(form, 网格, [行])` | 值按字段类型转换；字段不存在于元数据则直接失败，不尝试猜 |
| 存 | `save(form)` | 返回是否出现强控提示或必填提示；必填提示挂在根容器，需全局扫描 |
| 报 | `submit(form, 办理人)` | 成功信号任一出现即继续（关页签、询问窗、普通提示）；提示被关闭时改看数据状态 |
| 批 | `approve(单据, 角色, 意见)`、`reject(...)` | 先切换角色登录再处理待办；每个场景独占自己的单据，避免任务被别人处理 |
| 变 | `terminate(...)`、`withdraw(...)`、`retake(...)`、`reset(...)` | 对应 03 §4 的四类动作；各动作先读取流程当前节点再决定可用性 |
| 查 | `query(view, 条件)`、`read_rows(view)` | 查询视图是 Canvas，读数据走 SpreadJS 接口或导出文件，不读 DOM |
| 验 | `expect_ui(...)`、`expect_query(...)`、`expect_db(...)` | 见 §4 |

**不放进原语的事**：登录和切换角色属于运行环境动作，放在 `session` 里，不算业务原语，以免场景里出现账号信息。

## 4. 「验」的三种证据

| 证据 | 内容 | 规则 |
|---|---|---|
| 界面 | 字段值、状态、表格行 | 不以提示文案作断言依据，因为提示可被配置关闭，且 3 秒消失 |
| 查询 | 系统查询视图能否查到、数值是否一致 | 走 SpreadJS 接口或导出文件 |
| 数据库（只读） | 单据头状态字段，加业务结果表记录 | 通用模型为 `流程编号 → 单据头表 → 状态列 → 结果表`；审批完成的标志是状态值 3 且结果表有对应记录 |

补充规则：
- 状态值引用代码常量，不把中文状态写进 SQL；断言里不散落字面量 '3'，统一从「状态字典」配置读取。
- 异步下游（如转账指令约 10 秒延迟）：先断言存在性，再按配置的等待窗口轮询，超时算失败，不算通过。
- 授信类表 `ZJSXEDYE.F_ZT` 的取值口径有两套约定，在实测确认前，不得对该字段下通过性断言。
- 每个场景至少一个业务检查点，没有检查点不算通过（设计 v3 §2.2）。

## 5. 具名等待点

至少包含下列等待，每个等待点都有超时和失败说明：

- 表单渲染完成，且 JSON 已加载。
- 输入防抖结束（文本框约 800ms 内值未稳定）。
- 下拉弹层出现，并且归属当前控件，而不是页面上别的弹层。
- 网格数据加载完成，分页已同步。
- 提交成功信号（三种走向任一）。
- 弹窗出现或关闭（包括手动挂载到 body 的弹窗）。
- 页签切换后控件尺寸稳定。

## 6. 适配器规范

- 接口：`type`（对应元数据里的组件类型）、`set`、`get`、`state`。
- 注册：按组件类型字符串注册。核心适配器随核心库发布；本机扩展适配器放扩展层，**不得同名覆盖核心**。
- 覆盖顺序（先做）：文本、数字、日期、下拉掩码、远程下拉帮助、弹出表单帮助、复选、单选、网格、页签、按钮、窗口、提示。尚未确认内部结构的 `FormDateRangeField` 和网格内嵌放大镜，晚做，做前先用只读观察核对。
- 遇到未覆盖组件：返回「无适配器」状态，脚本阻塞，由智能体在扩展层补；不允许退化成猜选择器。

## 7. 配置模型

| 配置项 | 说明 | 位置 |
|---|---|---|
| 环境 | 系统地址、环境名 | `config/` 本机文件，不入库 |
| 账号与角色 | 每个角色一组登录信息 | 本机文件，口令不写进代码、日志、场景 |
| 数据库 | 类型（Oracle 或信创）、只读连接信息 | 本机文件 |
| 项目 | 项目名、定制菜单路径、定制表单 ID | 每项目一份，不改核心库 |
| 状态字典 | 流程编号到状态列、状态值、结果表的映射 | 每项目一份，来自代码常量 |
| 环境参数 | 提示形态、成功提示开关等 | 首次运行时从环境读取并记录 |

凭据的落地方式（本地配置文件，还是系统钥匙串）要和你确认，见 §10。

## 7.1 三层知识，框架不绑定任何模块

| 层 | 内容 | 位置 |
|---|---|---|
| 框架通用层 | 原语、适配器、表单解析、只读库、证据、状态断言模型 | `core/` |
| 模块知识层 | 某业务的表单、落库表、业务状态、特有的坑（案例） | 工作区 `knowledge/modules/` |
| 项目配置层 | 环境、账号、定制菜单、状态模型 | `config/` |

`core/` 里不出现任何业务表名、字段名或状态值，只出现通用机制。新增投资、发债、外汇、贷款等业务时，只在工作区新增模块案例、场景和项目配置，不改框架（`core/`）。流程的单据头表、主键列、状态列用 `tools/discover_bill.py` 从代码自动提取（全仓 340 个流程中 318 个可完整提取，18 个把状态列显式设为 null，4 个待查）。接入步骤见 工作区 `knowledge/modules/README.md`。

## 7.2 产品化与项目定制：环境会变，标定要能重复做

交付形态是「产品 + 项目定制」。给出的测试环境只是一个示例，之后会换环境、换项目、换产品版本，所以：

1. **环境不是常量。** 地址、账号、数据库只在本机配置里，换环境只换配置，不改库、不改场景。
2. **标定不是一次性的（已实现，`core/ifcat/calibration.py`）。** 适配器是否可用不是写死的开关，而是记录「在哪个产品版本、哪个项目、哪个环境上标定通过，何时标定，对应哪个核心库版本」，保存在 `results/calibration/` 下。标定逻辑是库函数 `run_calibration`；命令行入口要等登录和「开」原语在真实环境上标定后才能接上，目前还没有。
3. **运行前自检。** 场景启动前先检查：本场景用到的组件类型，在当前环境上是否有标定记录；没有或版本不符，就先提示重新标定，不直接跑场景。这样环境升级后选择器失效，会在运行前暴露，而不是表现为一堆莫名失败。
4. **产品基线与项目定制分开。** 产品标准的表单、字段、流程写进模块案例；项目定制（改过的表单、加的字段、定制菜单、定制流程）只进该项目的配置，不污染基线。定制表单与标准表单的差异，用表单 JSON 做离线比对即可发现。
5. **环境参数每次读取。** 提示形态、成功提示开关、精度参数等，随环境变化，每次运行前从环境读取并记录到结果里，不写死。

## 8. 核心库保护

按设计 v3 §3.2：只读加版本号，发布清单记录每个文件的哈希，运行前校验，被改动则拒绝运行；扩展层隔离；扩展进核心走提案；发版前全部自测样本通过。本文不再重复。

## 9. 通用性验收

沿用设计 v3 §5 的标准：新增验证样本时，只允许新增适配器，不允许改原语或脚本结构。如果必须改原语，先返工本设计。
