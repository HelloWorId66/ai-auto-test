# 产品与模块

写用例设计的第一步"弄清业务"时先读这份。只写长期不变的东西：产品定位、各模块管什么、业务对象怎么流转、跨模块的共同机制。具体规则、字段、提示文案仍去表单定义、测试库、知识库现查。

内容来自产品知识库、菜单树和产品代码（存款、授信、贷款、外汇、结算、流程平台）。各模块和共同机制不一致的地方单独写出来了；代码随版本变化，遇到和这里说的不一样，以真实系统为准，并写进 `unconfirmed`。

## 1. 产品定位

IFC 是境外财资管理软件，使用者是集团在境外的**财资中心**（集团境外资金的运营主体）和它服务的**成员单位**。

- **财资中心**在核心系统里办业务、做审批。
- **成员单位**通过网银自助发起一部分业务（如提款、还款、付款、存入）。授信、合同这类财资中心的决策不在网银开放；财资中心自己对银行的业务只在核心系统。
- 没有特别说明时，测试按核心系统来。

## 2. 两个方向：企业业务和公司业务

菜单上有两大块，很多功能成对出现，方向相反：

| | 企业业务 | 公司业务 |
|---|---|---|
| 是什么 | 财资中心为成员单位提供的服务 | 财资中心自己和银行等外部机构之间的业务 |
| 财资中心的角色 | 吸收存款方、放贷方、交易对手 | 存款人、借款人、交易方 |
| 成对的例子 | 企业定存、企业授信、企业贷款、企业外汇 | 银行定存、银行授信、银行借款、对外外汇 |

两边的单据骨架基本一样，**主体正好相反，资金走法也常常不同**：企业那边多走内部账户、生成内部转账指令；银行那边多走银行账户、生成待收付记录。测一边时可以参照另一边的用例结构，但主体、权限和资金出口要换过来。

## 3. 各模块管什么

| 模块 | 管什么 | 主要业务对象 | 对象的一生 | 和别的模块 |
|---|---|---|---|---|
| 账户管理 | 内部账户、财资中心银行账户、企业银行账户 | 账户 | 开户 → 变更 → 销户 | 所有资金收付都落在账户上；可用余额 = 余额 − 冻结 + 透支额度 |
| 结算（FT） | 内部付款、对外付款、集中付款；付企业款、扣企业款、银行付款；转账指令执行 | 付款单、转账指令、待收付记录 | 付款单：制单 → 审批 → 生成指令 → 执行 → 结果 | 各业务办结后的资金出口都汇到这里 |
| 存款（DP） | 企业定存（成员单位存在财资中心）、银行定存（财资中心存在银行）；一般、跃息、通知、隔夜 | 存单 | 存入 → 到期指示变更 / 续存利率维护 → 提前支取 / 到期处理（续存或转活期） | 前提是存款类型、周期、利率、管理账户已维护；到期由后台任务处理；银行定存可能占用授信 |
| 授信（LM） | 企业授信额度、银行授信额度；企业、银行综合授信合同 | 授信额度、综合授信合同 | 申请 → 变更 / 冻结 / 解冻 / 展期 → 终止（或到期自动终止） | 贷款合同、外汇交易、银行定存占用授信额度 |
| 贷款（LN） | 企业贷款、银行借款 | 贷款合同、提款 | 合同 → 提款 → 还款 / 展期 → 计息结息；合同可变更、终止 | 合同占授信，提款占合同；提款还款产生资金收付 |
| 外汇（FX） | 对内（成员单位与财资中心）、对外（财资中心与银行）的即期、远期、掉期、利率掉期、交叉货币掉期、无本金交割远期 | 外汇交易 | （可选）事前交易审批 → 交易 → 交割 / 展期 / 平仓 / 择期确认 / 定盘 | 可能占用授信；成交、交割生成资金收付 |
| 风险、数据分析（DA） | 支付风险预警、信用评级、风险指标、敞口分析 | 预警规则、指标 | 多为配置和查询 | 读取各业务数据 |
| 会计（AC） | 凭证生成、月末计提、账簿查询 | 凭证 | 业务办结 → 生成凭证 | 涉及账务的业务都会生成凭证 |
| 基础设置（BM） | 字典、汇率、利率、工作日历、银行信息、往来单位 | 基础数据 | 维护 | 几乎所有业务的前提数据 |
| 系统管理（SYS） | 用户角色、权限、流程配置、自动任务、系统参数 | — | — | 测试环境的前提：谁能做、流程有几个节点、开关怎么配 |

贸易融资、投资、发债、资金计划、公司间业务暂不纳入。

## 4. 跨模块的共同机制

这些规律在各模块里反复出现。知道了它们，就知道一张单据走到每一步该去看什么。

**1. 申请和结果分开。** 填的单据只是"申请"，审批全部通过的那一刻，才写进正式的存单、合同、额度、交易台账。没批完或被退回的单据，正式台账里看不到。变更类办结后是改原来那条台账，不是新加一条。
检查：办结前台账里没有（或没变），办结后才有（或才变）。

**2. 单据状态。** 平台统一的是 制单 → 审批中 → 审批完成，另有作废。只有退回或取回到**制单节点**，才回到制单；退回到中间节点仍是审批中。少数单据自己管状态，或者状态列名字不同。
检查：每一步之后状态对不对。

**3. 原对象锁定。** 变更、支取、还款、展期、冻结、终止这类"处理已有东西"的单据，一提交就把原对象锁住，退回或办结后放开。锁住期间再开一张同类单据处理它，会被拦住或选不到。授信还多一道：办结前别人改过原对象，再提交会被拦。
例外要留意：有的功能提交时不锁（如企业定存到期指示变更）；作废之后是否解锁，各功能不一定一致，值得测。
检查：提交后原对象被锁、另一张单据处理不了它；退回或办结后又能处理。

**4. 额度占用。** 授信是额度的源头。贷款合同、外汇交易（担保方式是授信时）、银行定存（开关打开时）占授信额度；提款占合同额度。时点统一：**提交时冻结，退回时解冻，办结时转为占用**；还款（循环合同）、合同终止时释放。每个事件按维度各记一条变动（总额度、品种、单位），办结时一次会记"解冻"和"占用"两条。
检查：提交、退回、办结三个时点，可用额度和冻结额度各变了多少；变动记录**条数和方向**对不对；额度不够时被拦。

**5. 新旧对象有关联，但编号不一定继承。** 变更、终止沿用原编号；提款按合同顺序编号；到期续存、展期、平仓会生成新的对象，用关联指回原对象，编号是新的。
检查：新对象能找回原对象，原对象的状态跟着变（如续存后原存单为已到期处理）。

**6. 资金出口。** 业务办结后要真正动钱，按结算账户类型走两条路：
- **内部账户**：生成内部转账指令（常见一收一付，或本金、利息、手续费各一条），稍后由系统自动执行记账。
- **银行账户**：生成待收付记录，之后转成付款单或指令，再发给银行。

指令执行是后来的事：内部指令一般几秒到十几秒后执行完；发往银行的指令在不连银行的测试环境里，通常停在"已发出、结果待查"，**不会自动变成成功或失败**。超时、通信异常、结果不明都不能当成付款失败。
检查：办结后生成了几条、金额和账户对不对；被退回的单据不生成；内部指令最终执行成功、余额变了。

**7. 到期和日终任务。** 到期处理、计息结息、到期还款、授信到期终止、外汇交割、日结，都是后台定时任务按系统日期做的，不是办结当场发生。任务一般逐笔处理，某一笔失败只记日志、不报错。授信到期终止这类任务直接生成一张已完成的单据，不走审批。
检查：分清哪些结果当场能看到，哪些要等任务跑过；任务相关的用例要写明依赖什么日期、什么前提数据。

**8. 配置开关。** 同一个功能在不同环境可能表现不同：授信控制开不开、外汇交易要不要事前审批、银行定存占不占授信、计息结息是自动还是手工、交割日遇非工作日是提醒还是拦截。开关存在系统参数里。
检查：测之前先确认这个环境的配置，预期按配置定，并写进用例设计的前提。

## 5. 测试环境的几个特点

- **结果和日期有关**：利率、汇率按日期取最新一条，工作日历决定起息日、到期日，月结、年结期间业务日期可能回到上月末。用例里不要把某个具体日期写死成预期，从当天推出来。
- **测试环境一般不连银行**：对外付款类只能检查到"指令已生成、已发出"，看不到银行结果。
- **后台任务不会为测试专门跑**：依赖任务的结果，要么等任务的运行时段，要么请管理员手工执行，用例设计里写明。
- **提示码和提示文案分开存**：代码里只有提示码，真实文案用 `ifc tool db_mcp messages` 查。

## 6. 怎么用这份背景

测一个功能前，先回答四个问题，写进用例设计的 `chain`：

1. 属于哪个模块，是企业业务还是公司业务？
2. 处理的是什么业务对象？在它一生里的哪一步？
3. 上游要先有什么（基础数据、上游对象、开关），下游会受什么影响（锁定、额度、资金出口、凭证）？
4. 第 4 节哪几条机制和它有关？每条在哪个节点检查？

答不上来的，去知识库查这个功能的需求、设计和代码（看第 4 节机制落在哪里，见 `查资料.md`）；还查不到，再用业务话问用户。
