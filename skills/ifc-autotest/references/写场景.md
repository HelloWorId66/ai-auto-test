# 写场景

场景是 YAML 数据，不是代码。业务人员审的是它渲染出来的 HTML 审核页。模板见同目录 `场景模板.yaml`。

**先有用例设计，后有场景文件。** 同一功能目录下的 `用例设计.yaml`（用 `ifc design` 生成页面给用户看）经用户确认之后，才按它一条用例写一个场景。还没有用例设计，或者用户还没确认，就回到 SKILL.md 的第一段。

## 放在哪

`scenarios/<模块>/<功能>/<场景>.yaml`。模块用代号（DP、LM、FT……）。同一功能目录下的场景会合在一张审核页里，方便业务人员看到完整覆盖面。

## 场景里要写什么

| 字段 | 含义 |
|---|---|
| `id` | 场景编号，整个工作区内必须唯一 |
| `title` | 标题，业务语言 |
| `module` | 模块代号 |
| `feature` | 所属功能。不写时取所在目录名 |
| `kind` | `主流程` 或 `核心异常` |
| `goal` | 这个场景要保证什么，一两句业务语言 |
| `source` | 依据：需求、设计、禅道用例、真实页面观察 |
| `unconfirmed` | 还没有证据的内容。审核页会标红，请业务确认 |
| `labels` | 技术名 → 业务名。只用于审核页和报告显示，让业务人员看到的是业务名称 |
| `preconditions` | 前提条件，业务语言 |
| `roles` | 角色代号 → 业务名称。角色代号要和环境配置里的账号对应（如 `maker`、`checker`） |
| `data` | 场景用到的业务数据，步骤里用 `${data.名字}` 引用 |
| `steps` | 步骤。每步有 `id`、`as`（哪个角色做）、`do`（动作）、`说明`（业务语言）、`args`（参数） |

`title`、`goal`、`说明`、`unconfirmed`、`preconditions` 会原样出现在审核页和报告上，**只写业务话**。为什么用了某个扩展动作、某个控件怎么定位这类技术原因，写在文件里的 `#` 注释里，不要写进这些字段。

## 动作清单

`args` 里必须给的参数写在括号里。字段标签必须取自表单定义（`knowledge/forms/<表单ID>.json`），不要凭印象写。

**操作类**

| 动作 | 做什么 |
|---|---|
| `open`（form） | 打开表单并新建一张单据 |
| `fill`（form, values） | 填写字段。`values` 的键是字段标签。金额字段写"币种 金额"，如 `HKD 100000`。同名标签用 `occurrence: 序号`（从 0 起）或 `within: 祖先组件key` 区分 |
| `fill_grid`（form, grid, rows） | 逐行填表格，填完立即读回核对。新增行给 `add_button: 按钮文字`；填系统已带出的行用 `existing: true` |
| `save`（form） | 保存。系统弹出失败提示或弹框拦住时，这一步判为没通过；只在字段旁边标红提示（如必填没填）而不弹框时，这一步照样算过，所以后面必须跟检查点 |
| `submit`（form） | 提交审批 |
| `approve`（bill） | 审核人在待办里逐个节点同意，直到单据离开本人待办。`bill` 是单据编号 |
| `reject`（bill） | 审核人在待办里退回（退回至制单） |
| `open_todo`（bill, form） | 在本人待办里打开单据，如被退回的单据 |
| `edit`（form） | 点"编辑"，让已保存或被退回的单据可以修改 |
| `pick_record`（form, find） | 在打开表单时自动弹出的"选择…"窗口里选一条。`find` 写能唯一识别那条记录的文字，如授信编号、存款编号 |
| `capture_field`（form, label, name） | 记下页面上的值（如系统生成的单据编号、授信编号），后面用 `${captured.name}` 引用。只读字段也能记 |
| `capture_db`（flow, key, column, name） | 从数据库的单据头里记下一个值，后面用 `${captured.name}` 引用 |

**检查点类**（每个场景至少一个）

| 动作 | 检查什么 |
|---|---|
| `expect_field`（form, label, expected） | 字段的值。联动计算的字段会自动多等几秒 |
| `expect_visible`（form, label, visible） | 字段当前是否显示 |
| `expect_grid`（form, grid, rows） | 表格内容，按行序比较，行数必须一致 |
| `submit_with_warning`（form, warning, then） | 提交时系统弹出含 `warning` 文字的提醒，按 `then` 按钮后继续 |
| `approve_blocked`（bill, message） | 审核人同意时被系统拦截，提示含 `message`，单据仍在待办 |
| `expect_flow_completed`（bill） | 单据出现在"已完成"里，且不在待办 |
| `expect_not_listed`（form, find） | "选择…"窗口里选不到这条记录（如已终止的对象） |
| `expect_query`（form, conditions） | 查询页的结果，见下文 |
| `expect_db_status`、`expect_db_record`、`expect_db_result` | 数据库里的结果，见 `数据库检查.md` |

工作区 `extensions/` 里用 `@action` 声明的扩展动作，用法和上面一样。

## 变量

| 写法 | 含义 |
|---|---|
| `${data.名字}` | 引用 `data` 里的数据 |
| `${captured.名字}` | 运行中记下的值 |
| `${today}`、`${today+30}`、`${today-1}` | 当天、30 天后、昨天 |
| `${today+12m}` | 12 个月后 |
| `${today+12m:compact}` | 同上，写成 `YYYYMMDD`（数据库里的日期列用这种） |
| `${unique}` | 每次运行自动生成的 14 位数字，一次运行内不变 |

- **日期不要写死**，否则隔天就过期。
- **单据不清理**。名称、摘要这类重复运行会撞车的数据用 `${unique}`，如 `名称: 自动化-${unique}`。

## 增量需求

新建一个场景文件，`extends: 基线场景id`，只写差异。基线按场景编号查找，可以在别的功能、别的模块目录里。

```yaml
id: DP-定存存入-新增字段X
extends: DP-定存存入-一般定期转活期
data: {new_field: "abc"}                    # 新增数据
set: {data.amount: "HKD 2000"}              # 改基线已有的数据
add_steps_after:                            # 在基线某一步后面插入步骤
  s2: [{id: n1, as: maker, do: expect_field, 说明: ..., args: {...}}]
remove_steps: [s4]                          # 去掉基线里的步骤
```

基线或增量场景任何一个被改动，两者的审核都失效。

## 变更、终止类功能

和新增一样是表单，流程也是 开 → 填 → 存 → 提交 → 审批。区别有两点：

1. **被操作的对象由场景自己先造**：`extends` 新增场景，办结后拿它的编号继续做变更或终止。
2. **打开表单会自动弹出"选择…"窗口**：用 `pick_record` 选刚造出来的那一条。已终止的对象应该选不到，用 `expect_not_listed` 检查。

同名字段常常出现两次（左边可改的新值、右边只读的原值），用 `occurrence` 区分。

## 查询页

```yaml
- id: q1
  as: maker
  do: expect_query
  说明: 按存款方查询，结果里有刚办结的这笔存款
  args:
    form: 查询表单ID
    conditions: {存款方: "${data.depositor}"}       # 键是页面上的条件名称
    rows: [{存款编号: "${captured.bill_no}", 存款金额: "1,000.00"}]   # 结果里必须有的行，键是表头
    count: 1                                        # 可选：结果行数，合计、小计行不算
    wait: 30                                        # 可选：结果异步出现时最多等多少秒
```

查询结果表格在页面上读不到文字，引擎是点"导出"下载 Excel 再按表头核对的，所以这个页面必须有"导出"按钮。

- **查询页也是一张表单**：先 `ifc forms import <查询表单ID> --from-env`，并在环境配置里给它配菜单路径，和业务表单一样。
- **`expect_query` 前面要有一步 `open` 打开查询表单**。审批完成后页面停在首页，不会自己跳到查询页。
- **`rows` 的键是导出 Excel 里的表头**，不是申请表单上的字段标签，两边常常不一样（如申请单上叫"授信金额"，查询结果里叫"授信额度"）。拿不准时先 `--draft` 试跑一次，在这次运行的结果目录里打开导出的 Excel 看真实表头。

## 检查"被拦截"怎么写

- 提交、审批时被系统拦截的：用 `submit_with_warning`、`approve_blocked`。
- 保存时被系统弹框或失败提示拦截、而这正是预期结果的：引擎没有自带"保存被拦截"的检查动作，`save` 会直接判为没通过。在 `extensions/` 里补一个动作（点保存，检查提示文字含预期内容），见 `排查与扩展.md`。
- 只在字段旁标红、不弹框的（必填没填）：`save` 之后检查"没有真的保存"，例如系统生成的编号仍然是空的：`expect_field`（label: 编号字段, expected: ""）。
- 预期的拦截没有出现：这是测试发现，不改预期，写进 `unconfirmed`，最多再试一次确认。

## 测试数据

- 用专用的测试主体和账户。用户没指定之前，沿用已有场景里的主体，并在 `unconfirmed` 里写明。
- 前提数据（如某个存款方、某个账号存在且余额充足）写进 `preconditions`。

## 写完之后

场景文件是在用户确认了用例设计（`用例设计.yaml`）之后才写的，步骤和预期要和它一一对应。

1. `ifc validate <场景>`：离线校验，不连环境。
2. `ifc run <场景> --draft` 在真实页面上试跑，把自动化本身的问题调通。系统的实际表现和用例设计不一致时，不改预期，写进 `unconfirmed`。
3. `ifc render <场景>`，把审核页交给用户，说明和用例设计相比有没有变化、试跑发现了什么，等明确答复。
4. 用户通过后 `ifc approve <场景>`，再正式 `ifc run <场景>`。
