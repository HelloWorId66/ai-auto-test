# 选用例

适用所有模块。写用例设计（第一段）时先读这份，再读 `产品与模块.md` 弄清这个功能在业务链上的位置。下文的例子只为说明意思，不是要照抄的清单。

同事反馈"AI 理解的业务不对"，多数时候不是规则理解错了，而是**测的不是日常会发生的事**：去测必填项、格式、单独的退回重提，真正每天在走的业务链反而没测到。选用例时按下面六条来。

## 1. 先弄清业务对象的一生，再按它铺用例

每个功能都在处理某个**业务对象**：一笔授信额度、一份合同、一笔提款、一张存单、一笔外汇交易、一笔付款。先弄清这个对象从生到灭要经过哪些功能，比如：

- 申请 → 变更 → 冻结 / 解冻 → 终止
- 合同 → 提款 → 还款 / 展期
- 存入 → 到期指示变更 → 支取或到期处理
- 交易 → 交割 / 展期 / 平仓

然后：

- 测某个功能时，它要处理的对象**由用例自己从上游功能做出来**，记下编号交给后面的步骤用；不借环境里碰巧存在的数据。
- 一次要测一组功能时，按这条链的顺序排，上游用例就是下游用例的前提。

## 2. 一条用例对应一种真实的业务形态

业务形态从业务上分，不从字段上分。常见的切分方式：

- 按品种、类型：单品种 / 多品种，一般 / 通知 / 跃息
- 按方式：循环 / 不循环，一次提款 / 多次提款
- 按定价：固定利率 / 浮动利率
- 按主体：一个申请人 / 多个共同申请人；本币 / 外币
- 变更类按"改了什么"分：新增一项、增加金额、减少金额、删除一项

只挑**生产中常见**的形态，不做排列组合，不凑数。用例条数由形态决定。

**不写这些用例**：必填项没填被拦截、格式校验、字段长度、边界值。它们是表单配置，测了也说明不了业务对不对。

## 3. 退回、取回放在主流程中间测

不单独写"退回后重提"这种用例。在某条主流程提交之后插入一次退回（或取回），检查单据回到制单、被它锁住的对象已解锁、冻结的额度已释放，然后继续把这条主流程走完。一条用例同时验证了正常路径和回退。

## 4. 每个节点检查"该发生的事正好在这一步发生"

不只看最后办结。每走一步，检查这一步该有的变化出现了，不该有的还没出现：

| 节点 | 应该看到 | 这时还不该看到 |
|---|---|---|
| 保存 | 单据存在，状态是制单 | 业务结果、余额变化 |
| 提交 | 状态变审批中；被它处理的原对象被锁定；该冻结的额度已冻结 | 业务结果生效 |
| 中间节点同意 | 仍是审批中，进入下一节点 | 业务结果生效 |
| 退回 / 取回到制单 | 回到制单；原对象解锁；冻结释放 | — |
| 审批通过 | 状态完成；业务结果生效（结果台账、余额、变动记录的**条数和方向**都对）；原对象状态跟着变 | 重复的、多出来的记录 |

- 预期值从输入数据和业务规则推出来，不从页面或数据库抄。
- 终止、停用这类操作：状态要变，同时检查**不该被清掉的没有被清掉**（比如授信终止后额度数据仍保留）。

## 5. 办结后看对外的结果

- 查询页能查到，状态、金额、日期正确。
- 对下游的影响：该生成的东西生成了（转账指令、待收付记录、回单、可用余额变化）；下游功能能选到或选不到这个对象。
- 分清当场的和后来的：转账指令的执行结果、到期处理、计息结息是后台任务后来做的。依赖它们的检查，用例设计里写明"要等多久"或"要等任务跑过"；测试环境不连银行时，对外付款只检查到指令已生成、已发出。

## 6. 异常只测业务上的联动约束

测"上游状态变了之后，下游该不该还能做"：

- 终止、冻结之后不能再用；解冻之后又可以用
- 额度、余额不够时被拦截
- 被一张单据锁住的对象，另一张单据选不到或提交被拦

依据是需求里的业务规则，以及 `ifc tool db_mcp messages` 查到的真实提示文案。

## 写进用例设计时

用例设计按"**业务链 → 业务形态 → 每个节点的检查**"来组织（模板见 `用例设计模板.yaml`）：

- `chain`：这个功能处理的业务对象、上游要先有什么、下游会影响什么、涉及哪几条共同机制。
- 每条用例的 `form` 写对应哪种业务形态，`object_from` 写对象从哪里来（本用例新建，或由哪条上游用例做出来）；每一步的 `expect` 写这个节点该看到什么、还不该看到什么。
- `not_tested` 里写明为什么不测（例如：必填校验属于表单配置）。
