# 查资料

你自己去查，不要让用户安装或配置任何东西。地址这类信息由团队提供，通过环境变量给出，不写进工作区的入库文件。

## 资料来源，按可信程度

| 来源 | 用来查什么 |
|---|---|
| 用户给的需求、设计、禅道用例 | 业务目的、规则、异常。有就用，没有也能做 |
| 表单定义（`knowledge/forms/<表单ID>.json`，从被测环境导入） | 页面上有哪些字段、标签、必填、下拉、表格、按钮 |
| 测试库的配置元数据 | 菜单路径、真实提示文案、下拉选项、数据库列的中文名 |
| 团队知识库（代码和文档） | 后端的业务规则、联动、校验、码值常量、落库逻辑、每个节点做什么 |
| 真实页面 | 实际的交互和结果。和文档不一致时以它为准 |
| 用户 | 以上都查不清时，用业务话问 |

## 表单定义

```
ifc forms import <表单ID> [<表单ID>...] --from-env [--env dev]
ifc forms list
```

**表单定义从被测环境读取。** 这条命令用环境配置里的账号登录，向环境要这个表单的定义（页面自己打开表单时走的是同一个接口），存进工作区 `knowledge/forms/`，随工作区入库。拿到的就是环境上实际部署的那一版，客户化定制的表单也在内。不需要本机有产品代码，不要为了表单定义去向用户要代码、要文件。

- 前提是 `config/local/<环境>.yaml` 已配好且 `ifc doctor --login` 通过。产品版本取配置里的 `product_version`，没填就加 `--product-version`。版本号以 `ifc doctor --login` 输出的"登录后的页面标题"为准（如标题是"…【测试V6.2.7-SNAPSHOT】…"就填 `6.2.7-SNAPSHOT`），不要填前端包号或日期。
- 提示"没有取到"时，环境上确实没有这个 ID 的表单：先用 `ifc tool db_mcp entries <菜单名>` 核对表单 ID，再确认这个环境部署了该功能。还是没有就如实告诉用户，不要换别的途径硬找。
- 环境升级后表单可能变了，重新导入一次即可覆盖。
- 备用：手上有产品代码时，也可以 `ifc forms import <表单ID>... --from <产品表单定义目录> --product-version 6.2.7`。

## 测试库的配置元数据（只读）

需要环境变量 `IFCAT_DB_MCP_URL`（测试库查询服务的地址）。

```
ifc tool db_mcp entries <功能号|菜单名|表单ID>      菜单入口和完整菜单路径
ifc tool db_mcp messages <表单ID|功能号|文字>       系统真实的提示文案（写核心异常的预期用）
ifc tool db_mcp columns <业务表名>                  每一列的中文含义（写数据库检查前先看）
ifc tool db_mcp mask <掩码key>                      下拉选项
```

这个工具只放行只读查询。**如果你是通过自己的 MCP 连接直接访问这个服务，注意它带写入类工具，绝对不要调用 `execute` 开头的工具。**

它读的是配置元数据，读不到业务表里的数据（如存款申请记录）。业务数据走环境配置里的只读数据库账号，见 `数据库检查.md`。

## 团队知识库

查业务代码、流程、公共方法、业务文档。优先用你自己环境里已经配置的知识库 MCP。没有的话，设置环境变量 `IFCAT_KB_MCP_URL` 后用：

```
ifc tool kb_query <工具名> '<JSON 参数>'
```

知识库只收录代码，不收录表单定义文件（已核实），不要去知识库里找表单定义，用上面的 `ifc forms import --from-env`。

## 从代码看一个功能在每个节点做什么

第 4 节共同机制（锁定、额度、资金出口……）具体落在哪一步，看后端代码最准。代码从团队知识库查：优先用你自己环境里已经配置的知识库 MCP，没有就用 `ifc tool kb_query`（见上一节）。不要假设本机有产品代码，也不要向用户要代码。

- **流程类**：每个流程有一个流程类，一般命名为 `funds.pansoft.svr.flow.impl.<流程编号>`，继承平台的流程基类。看它的几个回调：
  - 从制单提交（`processSubmitFromStart`）：通常在这里锁原对象、冻结额度。
  - 退回或取回到制单（`processBackToStart`）：解锁、解冻。
  - 最后一个节点同意（`processSubmitToEnd`）：写结果台账、占用额度、生成转账指令或待收付记录。
  - 作废（`processBreak`）：看它有没有解锁、释放。
- **表单校验类**：`FormMovement<单据类型>`，保存、提交前的业务校验和提示码在这里，提示码的真实文案用 `ifc tool db_mcp messages` 查。
- **新旧两套并存**：有的模块同时有新旧两套流程类，实际用哪一个看流程配置。拿不准时以真实系统的表现为准。
- **后台任务**：到期、计息、日结这类任务的类名一般以 `Task` 结尾，看它挑哪些数据（到期日、状态、是否锁定），就知道测试数据要准备成什么样。

从代码得到的是"系统打算怎么做"。写进用例设计时作为依据（`source` 写"产品代码"），最终以真实系统为准；两者不一致的，记进 `unconfirmed`，可能就是产品问题。
## 单据模型骨架

```
ifc tool discover_bill --root <产品代码根目录> <流程编号> [<流程编号>...]
ifc tool discover_bill --root <产品代码根目录> --list [--module DP]
```

从业务代码里提取流程的单据头表、主键列、状态列，只读代码，不连数据库。结果表要读代码补充。用法见 `数据库检查.md`。

## 在真实页面上探查

**写用例设计之前**只用 `ifc view <表单ID> --options`：打开表单的新建页，列出字段是否显示、必填、能否填、默认值、可用按钮，把下拉和弹层选择字段点开列出真实选项，并截图。它不填写、不选择、不保存，环境里不会多出单据。申请人、币种这类"有哪些可选"的问题从这里得到答案，不要去问用户。

**用例设计确认之后**，才可以用 `ifc run <场景> --draft` 跑到某一步看截图和报告。试跑会在测试环境里留下单据，属于测试数据，汇报时要告诉用户留下了哪些。**不要在生产环境做。**
