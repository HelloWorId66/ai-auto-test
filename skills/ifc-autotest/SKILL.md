# IFC AI 自动化测试

面向零技术背景的业务、实施人员。**用户只说业务话。技术问题（找不到控件、环境慢、缺组件）你自己解决，不拿来打扰用户。**

## 这套东西怎么运转

- **用例就是数据**：一个业务场景写成一个 YAML 文件（谁、做什么、检查什么）。引擎直接照着它操作真实页面，**不需要再写脚本**。
- **先定用例，再做自动化**：先用业务话写出"测什么、怎么测、预期是什么"的用例设计，生成 HTML 页面给业务人员看，业务人员确认后，才动手做自动化。
- **先审后跑**：做好的用例渲染成业务人员看得懂的 HTML 审核页，业务人员在对话里说"通过"之后才能正式运行。用例一改，审核自动失效，要重新审。
- **工作区**：一个项目的用例、配置、结果放在一个目录里（有 `workspace.yaml` 的目录）。本技能自带引擎，不需要另外安装框架。

## 命令入口

`<技能目录>` 是本文件所在的目录。下文的 `ifc` 一律指：

```
python3 <技能目录>/scripts/ifc.py <命令> [参数]        （Windows 上用 python）
```

在工作区目录里运行；不在工作区里时加 `--workspace <工作区目录>`。

**运行环境由你负责准备好，不要让用户自己去装：**

1. 先确认本机有 Python 3.10 或更高版本：依次试 `python3 --version`、`python --version`，Windows 上再试 `py -3 --version`。哪个能用，后面就用哪个来运行 `scripts/ifc.py`。
2. 都没有，或者版本低于 3.10：告诉用户"需要先装一个 Python，我来装，可以吗"，得到同意后你来安装。macOS 用 `brew install python@3.12`（没有 brew 就从 python.org 下载安装包）；Windows 用 `winget install Python.Python.3.12`。装完重新开一个终端再确认版本。
3. 其余的（依赖和浏览器，约 200 MB）在第一次运行 `ifc` 命令时自动下载安装，需要联网，要几分钟，只做一次。开始前跟用户说一声"第一次要准备环境，稍等几分钟"。失败时命令会说明原因和日志位置，多半是网络问题，处理后重新执行同一条命令即可。

## 开始前

1. **找工作区**：当前目录或上级目录里有 `workspace.yaml`。没有就向用户确认项目名后执行 `ifc init <目录> --project <项目名>`。
2. **自检**：`ifc doctor --login`。未通过的项按输出里的"怎么办"自己处理。缺环境地址、账号、口令时才问用户，写进工作区 `config/local/<环境>.yaml`（该目录不入库；`product_version` 填 `ifc doctor --login` 输出的"登录后的页面标题"里的版本号，如 `6.2.7-SNAPSHOT`；测试环境在内网，口令可以直接写，也可以用 `password_env` 指向环境变量）。
3. **标定**：第一次到一个环境，或换了产品版本、界面语言、技能版本之后，先 `ifc calibrate`。没标定时运行会直接提示。

## 完整流程（必须照做，顺序不能换）

分三段。**每一段结束都要停下来等用户，不许自己接着往下做。**

### 第一段：弄清业务，写出用例设计，请用户确认

1. 用户说要测某个功能。可能附需求、设计、禅道用例，也可能什么都没有。
2. **弄清业务，只看不动**：先读 `references/产品与模块.md`，弄清这个功能属于哪个模块、处理什么业务对象、在业务链上的哪一步 → 读用户给的资料 → 查知识库和测试库（只读）→ `ifc forms import <表单ID> --from-env` 取表单定义 → `ifc view <表单ID> --options` 看真实页面（哪些字段显示、哪些必填、能不能填、默认值、可用按钮、下拉里有哪些选项，附截图）。**能自己查到的不问用户**（下拉里有什么选项、字段是否必填、菜单在哪）；查不到的业务问题，才用业务话问用户。怎么查见 `references/查资料.md`、`references/识别页面.md`。
3. **写用例设计**：先按 `references/选用例.md` 选用例，再写 `scenarios/<模块>/<功能>/用例设计.yaml`，照 `references/用例设计模板.yaml` 写，全部用业务话。内容是：这个功能在业务链上的位置、业务规则和依据、准备测哪几条用例（每条的前提、操作步骤、预期结果、测试数据）、哪些不测及原因、需要业务确认的问题。测试数据写具体的值（下拉选项用 `ifc view --options` 看到的真实选项），不写"从下拉中选一个"。
4. **生成用例设计页面，请用户在页面上审**：`ifc design <模块>/<功能>` 生成 HTML 页面（在 `reviews/` 下），把页面的完整路径告诉用户，请他打开看。对话里只附三五句摘要（准备测哪几条、有哪些问题要他确认），**不要把整份用例设计用文字贴在对话里代替页面**。用户提了修改意见：改 `用例设计.yaml`，重新 `ifc design`，再请他看。
5. **等用户确认。用户确认之前，不许做下面这些事**：写场景文件、标定、试跑、写扩展、在环境里保存或提交任何单据。

### 第二段：把确认过的用例做成自动化，调通

6. 按确认过的用例设计，一条用例写一个场景文件 `scenarios/<模块>/<功能>/<场景>.yaml`，步骤和预期与用例设计一一对应。写法见 `references/写场景.md`。
7. `ifc validate` → 需要时 `ifc calibrate` → `ifc run <场景> --draft` 试跑，直到自动化本身没有问题。技术问题自己解决（见 `references/排查与扩展.md`），不打扰用户。
8. 试跑中发现系统的实际表现和用例设计不一致（规则没生效、字段不一样、流程节点不同）：**这是测试发现，不是要你去凑通的问题**。不改预期，记进场景的 `unconfirmed`，同一个疑点最多再试一次确认，不要换着法子反复试，每试一次环境里就多一张单据。
9. `ifc render` 生成审核页。向用户说明三件事：审核页在哪；和已确认的用例设计相比有没有变化（没有就说没有）；试跑里发现了什么。

### 第三段：用户说"通过"，正式运行

10. **等用户在对话里明确回复"通过"**，或者提修改意见。通过后才执行 `ifc approve <场景>`。
11. `ifc run <场景>` 正式运行。
12. 如实汇报：通过几个、检查未通过几个（附现象和截图路径）、报告在哪、这次在环境里留下了哪些单据（编号和状态，特别是提交后还停在别人待办里的）。
13. 之后用户可以随时重跑：单个场景、单个模块（`--module DP,LM`）、全部（`--all`）。每次生成新的批次报告，历史不覆盖。

用户只是要重跑已有用例、看报告、或改某条已有用例时，不必从第一段开始；新增功能、新增用例时必须从第一段开始。

## 铁律

- **用例设计和做好的用例，都是生成 HTML 页面给用户审**（`ifc design`、`ifc render`），不用对话里的大段文字代替。
- **用例设计没确认，不做自动化**。不写场景文件、不标定、不试跑、不写扩展、不在环境里留单据。
- **绝不自行审批**。只有用户在对话里明确说通过，才能执行 `approve`。
- **审核后改了用例，就必须重新审**。排查时需要改已审核的用例（哪怕只改一个标签），改完要重新 `render` 并请用户再确认；在那之前只能用 `--draft` 调试，`--draft` 的结果不能当结论。
- **系统报错不放过**。检查点没通过，说明系统行为和预期不一致，是疑似产品问题：如实上报，**不改预期让它通过**。
- **只相信证据**。需求文档、表单定义、测试库配置、真实页面、业务确认，这些才算证据。没有证据的内容写进用例的 `unconfirmed`，不替业务做决定。需求文档和真实系统不一致时，以真实系统为准，并把差异写进 `unconfirmed`。
- **预期值要推出来，不能抄回来**。检查值必须来自输入数据或业务规则，不能把页面或数据库里查到的值直接当预期。
- **给业务人员看的文字只用业务话**。用例设计、场景里的 `title`、`goal`、`说明`、`unconfirmed`、`preconditions` 会出现在审核页和报告上，不写组件名、类名、扩展、选择器这类技术内容；技术上的原因写在场景文件的 `#` 注释里。
- **工作区保持干净**。排查用的临时脚本和抓下来的文件放在工作区的 `tmp/` 目录（不入库），用完删掉；没被任何场景用到的扩展删掉。
- **不改引擎**（技能目录下的 `engine/`，改了会被完整性校验拦住）。缺控件、缺动作在工作区 `extensions/` 里补。
- **数据库只读**；不对生产环境运行；口令不写进用例、日志、报告。
- 只支持 React 表单。老式（GWT）表单不在范围内，遇到时告诉用户。

## 写什么样的用例

完整标准见 `references/选用例.md`，要点：

- 测**生产中天天在走的业务链**。一条用例对应一种常见的业务形态（品种、方式、主体……），用例条数由形态决定，不做排列组合。
- 不写必填、格式、长度、边界值这类用例，它们是表单配置，说明不了业务对不对。
- 退回、取回不单独成用例，插在某条主流程中间测，然后把主流程走完。
- 每个节点检查"该发生的事正好在这一步发生"：提交时锁定、冻结；退回时释放；办结时结果生效、记录条数和方向都对。**主流程不能只检查"办结"**。没有检查点的场景判为无效。
- 异常只测业务上的联动约束（终止、冻结后不能再用，额度、余额不够被拦截，被锁住的对象选不到）。
- 变更、终止这类功能要操作的对象，**由用例自己从上游做出来**，不依赖环境里恰好有的数据。

## 结果怎么判读

| 状态 | 含义 | 你该做什么 |
|---|---|---|
| passed | 检查全部通过 | 汇报 |
| failed | 检查点没通过，系统行为和预期不一致 | 如实上报，附截图；不改预期 |
| blocked | 自动化没能完成（定位、等待、超时、数据、环境） | 自己排查修复后重跑。确认是系统自己报错或卡住的，按疑似产品问题上报 |
| invalid | 场景没有检查点 | 补检查点 |
| skipped | 场景没审核，没有运行 | 提醒用户审核 |

一个场景在第一个没通过的步骤处停止，后面的步骤不执行；批次里的其他场景照常运行。两类失败都有截图。

## 命令速查

```
ifc init <目录> --project <项目名>                     新建工作区
ifc doctor [--login] [--env dev]                       环境自检
ifc list [--module DP]                                 场景和审核状态
ifc validate <场景> | --module DP | --all              离线校验，不连环境
ifc render <场景> | --module DP | --all                生成 HTML 审核页（写入 reviews/）
ifc approve <场景>                                     用户说"通过"之后才执行
ifc run <场景> | --module DP,LM | --all [--env dev] [--draft]
ifc calibrate [--env dev]                              组件标定
ifc forms import <表单ID>... --from-env [--env dev]     从被测环境读取表单定义
ifc forms list                                         已导入的表单定义
ifc design <模块>/<功能>                               把用例设计生成 HTML 页面（写入 reviews/），给用户确认
ifc view <表单ID> [--options] [--env dev]              只看不动地查看真实表单（字段、默认值、按钮、截图；--options 列出下拉选项）
ifc ui --workspace <工作区>                            本地运行页面
ifc tool db_mcp|kb_query|discover_bill <参数>          查资料的辅助工具，见 references/查资料.md
ifc version                                            技能版本和运行环境位置
```

- `<场景>` 可以是文件路径、相对 `scenarios/` 的路径，或文件名。
- 退出码：0 全部通过；1 有场景没通过、有校验错误、有组件标定失败或自检有未通过项；2 用法或配置有误，没有开始执行；3 没有运行任何场景（如场景未审核）。
- 报告：`results/index.html` 是历史索引；每个批次在 `results/runs/<项目>/<环境>/<批次>/report.html`。
