# IFC AI 自动化测试（智能体规程）

面向零技术背景的业务/实施人员。**用户只说业务话；技术问题（定位不到控件、脚本写不出来、环境慢）你自己解决，不拿来打扰用户。**

## 0. 先弄清三件事
1. **工作区**：当前目录或上级里有 `workspace.yaml` 的目录。没有就让用户确认后执行 `ifc init <目录> --project <项目名>`。
2. **命令入口 `ifc`**：框架里的 `ifc.py`。位置写在工作区 `workspace.local.yaml` 的 `framework`（本机文件，不入库）。下文 `ifc ...` 即 `python <framework>/ifc.py --workspace <工作区> ...`。
3. **环境是否可用**：先跑 `ifc doctor --login`。未通过的项，按"怎么办"自己处理；需要账号口令/地址时才问用户，口令写进工作区 `config/local/<环境>.yaml`（该目录不入库，测试环境内网，允许直接写）。

## 1. 完整流程（用户定义，必须照做）
1. 用户说要测某功能（可能附需求、设计、禅道用例，也可能什么都没有）。
2. **你自己想办法写出业务用例**：读给的资料 → 查知识库/代码 MCP、测试库 MCP（只读）→ 在真实界面上探查（见同目录 `组件识别方法论.md`）→ 必要时用业务语言问用户。
3. 写入 `scenarios/<模块>/<功能>/<场景>.yaml`，运行 `ifc validate`，再 `ifc render --module <模块>` 生成 HTML 审核页（`reviews/`），把路径给用户。
4. **等用户在对话里明确回复"通过"**（或提修改意见）。通过后才执行 `ifc approve <场景>`。**绝不自行审批。**
5. 审核通过后你自动完成：生成脚本所需的一切、`ifc run`、**全部跑通**。中间的 `blocked`（自动化未能完成）自己查原因修好；不要反复问用户。
6. 如实告诉用户结果：通过几个、检查未通过几个（疑似产品问题，附现象和截图路径）、报告位置。系统报错 = 疑似产品缺陷，**不改预期、不放过**；该场景标记，其余继续。
7. 后续用户可随时重跑：单场景 / 单模块（如 `--module DP,LM`）/ 全系统（`--all`）。每次生成新批次报告，历史不覆盖。

## 2. 写用例的规则
- 只写**核心的、生产中天天会遇到的业务场景**，含必要的核心异常（如余额不足被拦截、审核退回后重提）。**不写**边界值、冒烟。一个功能可以有多个场景。
- 每个场景必须有业务检查点（`expect_*` 等）；每个场景写 `goal`（保证什么）、`source`（依据）、`unconfirmed`（没有证据的内容）、`labels`（技术字段名→业务名）、`feature`、`kind`（主流程/核心异常）。
- **只相信证据**：需求文档、表单定义、测试库配置（消息表、菜单、掩码）、真实界面观察、业务确认。没有证据的写进 `unconfirmed`，不替业务做决定。需求文档与真实系统不一致时，以真实系统为准，并把差异写进 `unconfirmed`。
- 增量需求：新建场景 `extends` 基线，先跑受影响主线，再加新字段检查点。基线按场景 id 查找，可以在别的功能目录里；增量里 `data:` 新增数据、`set:` 改基线已有数据、`add_steps_after:` 在基线某步后插入步骤。
- **变更、终止、查询类功能**：它们和新增一样是 React 表单，沿用 开→填→存→报→批 的流程，区别只有三点：① 被变更/终止的对象要先存在，**由场景自己先造**（`extends` 新增场景，办结后拿它的编号继续），不依赖环境里恰好有的数据；② 打开表单会自动弹出「选择…」窗口，用 `pick_record`（`find` 写能唯一识别那条记录的文字，如授信编号/存款编号）选一条；已终止的对象选不到用 `expect_not_listed`；③ 查询页用 `expect_query`。
- **查询页**：条件区是普通表单控件，按界面上的条件名称填（`conditions: {存款方: xxx}`，下拉/多选/输入框自动识别）；结果表是画布渲染读不到文字，框架点「导出」下载 Excel 再按表头核对。`rows` 是结果里必须有的行（`{表头: 值}`），`count` 是行数（合计/小计行不算）。结果异步出现时加 `wait: 秒`。有的老查询页（GWT 渲染，如旧版「企业定存明细查询」的条件控件 id 形如 `FormTextInput_CKBH-input`）条件区仍是普通 input，也可用，但不在支持承诺范围内。
- **日期**：场景数据里可写 `${today}`、`${today+365}`（天）、`${today+12m}`（月）、`${today-1}`，运行时按当天推算；数据库里的日期列是 `YYYYMMDD`，用 `${today+12m:compact}`。不要把日期写死，否则隔天就过期。
- **单据头表被多种单据共用**（如授信申请/变更/终止同表，靠单据类型区分）：在 `bills/*.bills.yaml` 的流程里写 `where: {F_DJLX: "30020052"}` 限定。办结后单据编号会变（如授信编号不变但变更单据有自己的编号），用 `capture_db` 从库里取出再用于 `expect_flow_completed`。
- 只支持 React 表单；GWT 老表单不处理。
- **不重复的数据**：单据不清理，名称、摘要这类重复运行会撞车的数据，用 `${unique}`（每次运行自动生成的 14 位数字，一次运行内不变），如 `名称: 自动化-${unique}`。
- 动作清单见 `<framework>/core/ifcat/scenario.py` 的 `STEP_SPECS`，加上工作区 `extensions/` 里用 `@action` 声明的扩展动作；字段标签必须取自表单定义（`knowledge/forms/<表单ID>.json`，可用 `ifc forms import` 导入）。
- 测试数据：用专用测试主体/账户；单据不清理，靠环境定期刷新。用户未指定专用主体前，沿用场景里已有主体并在 `unconfirmed` 标明。

## 3. 结果判读
| 状态 | 含义 | 你该做什么 |
|---|---|---|
| passed | 检查全部通过 | 汇报 |
| failed | 检查未通过，系统行为与预期不一致 | 如实上报，附截图；不改预期 |
| blocked | 自动化没能完成（定位、等待、超时、数据、环境） | 自己排查修复，重跑；修不了才说明原因。排查后确认是系统自己报错或卡住，按疑似产品问题上报 |
| invalid | 场景没有检查点 | 补检查点 |
| skipped | 场景未审核，没运行 | 提醒用户审核 |

`--draft` 只用于调试未审核场景，结果不能当回归结论。

## 4. 排查 blocked 的顺序
1. 看批次报告里该场景的截图和错误文字（出错时会自动留页面截图）。
2. 页面空白/502：本机代理或环境问题（框架默认直连浏览器，不走系统代理）。
3. 找不到字段/菜单：核对表单定义和 `config/local/<环境>.yaml` 的菜单路径；菜单路径用 `python tools/db_mcp.py entries <表单ID或菜单名>` 取（home=核心系统、ebank=网银，按 home 的为准），它会按菜单编号前缀补全各级父菜单。
4. 填值无效或被联动清空：见方法论文档"已知坑"。
5. 框架缺控件适配器或缺动作（如撤回、上传附件）：**不要卡住，也不改框架 `core/`**。在工作区 `extensions/` 里补一个文件，只从 `ifcat.ext` 导入：控件写 `Adapter` 子类；动作写 `@action("名字", required=[...], text="业务说法", checkpoint=True/False)` 修饰的函数 `(ctx, **参数)`，返回 `StepResult.passed/failed/blocked`，`ctx.page` 是页面、`ctx.prim` 可复用内置原语、`ctx.screenshot()` 留截图。选择器必须来自真实页面观察。补完后场景里直接用，完成当次工作；归纳进框架由维护者定期做（`ifc harvest`），不是你的事。
6. 首次到新环境/新产品版本/新语言：先 `ifc calibrate`。

## 5. 外部信息源（智能体自行连接，不要让用户装）
- **代码/知识库 MCP**（`pansoft-team-knowledge`）：查业务代码、流程、公共方法。地址由团队提供；框架脚本 `tools/kb_query.py` 读环境变量 `IFCAT_KB_MCP_URL`。
- **测试库 MCP**：配置元数据库，**只读**：`findMenuPaths`、`findFormEntries`、`findFlows`、`findMessages`（真实提示文案）、`findMasks`/`getMaskDetail`（下拉选项）、`getFieldDetail`。**该服务带写工具，绝对不要调用 `execute*` 类工具。**业务表（如存款申请表）MCP 读不到。
- **业务库只读直连**（环境配置 `db:`，口令用 `password_env`，不要写进文件）：办结后用 `expect_db_status`（单据状态，`state: not:xxx` 表示不是某状态）、`expect_db_record`（`table: head` 查单据头，或 bills 里登记的结果表；`expect` 写列名=值，`absent: true` 表示不应存在，`wait: 秒` 等后台异步生成，如转账指令）。单据靠界面记下的单据编号定位，关联关系写在工作区 `bills/*.bills.yaml`。**检查值必须由输入数据或业务规则推出，不能把库里查到的值抄回来当预期**；**列和码值含义按这个顺序确认，别按列名猜**：① `python tools/db_mcp.py columns <表名>` 看平台元数据里的中文列名（如 `F_NDQTS`=下一个定期天数，`F_CKTS`=存款天数；元数据可能不全）；② 码值（如到期指示 1/3）元数据没有，用代码知识库 MCP 查后端代码里的常量和判断；③ 仍不确定，用只读查询的真实数据对照界面；④ 还不行就用业务语言问用户/客户，并写进 unconfirmed。
- **表单定义**：代码知识库 MCP 没有 ReactFormSpace 的 JSON（已核实：图谱里没索引任何 json，develop 图谱状态为失败，6.2.5 图谱早于该表单），表单仍用 `ifc forms import` 从产品代码导入；知识库用来查前后端代码里的业务规则、联动、校验、码值。
- 你的运行环境没有这些 MCP 时，按你自己的方式安装/配置；不要把配置工作交给业务人员。

## 6. 命令速查
```
ifc doctor [--login] [--env dev]          环境自检
ifc list [--module DP]                    场景与审核状态
ifc validate --module DP                  离线校验
ifc render --module DP                    生成 HTML 审核页
ifc approve <场景>            用户在对话里说"通过"之后才执行
ifc run <场景> | --module DP | --all [--env dev] [--draft]
ifc calibrate [--env dev]                 组件标定（换环境、产品版本、界面语言或框架版本后都要重做）
ifc forms import <表单ID>... --from <目录> --product-version 6.2.7
python <framework>/ui/server.py --workspace <工作区>   本地简单页面
```
报告：`results/index.html`（历史索引）→ `results/runs/<项目>/<环境>/<批次>/report.html`。

## 7. 边界
- 数据库只读；不改框架 `core/`（缺东西在工作区 `extensions/` 补）；不替用户审批；不把口令写进场景、日志、报告；不对生产环境运行。
